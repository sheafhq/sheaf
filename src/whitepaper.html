Technical Whitepaper · Version 1.0

The Sheaf Architecture: Verifiable Evidence for Autonomous Agents

13 November 2026 · Sheaf · api.sheafhq.io
Abstract

AI agents now initiate payments, change records, and call tools across third-party systems at machine speed. The evidence available when those actions are disputed is usually an application log: mutable, debugging-oriented, and controlled by the party that owns the system. Sheaf closes that gap with an out-of-process recorder that captures MCP tool calls at the boundary, signs them with Ed25519 keys the agent never holds, links them into a hash chain, and anchors Merkle epoch roots on Base L2. A portable .sheaf bundle can then prove a specific action to an auditor, issuer, or counterparty through selective disclosure — without exposing the rest of the chain and without trusting Sheaf's servers.

01The Trust Gap

Application logs are built to help engineers debug software. They are not built to survive an adversarial review. A log line can be edited at the source, rewritten in a database, dropped by a retention policy, or reconstructed from a different model version. Even an honest operator usually cannot prove that the log it presents is the same log its systems produced at execution time.

Observability platforms improve search and retention, but they preserve the same trust model: the operator owns the pipeline, the timestamps, and the storage. An auditor who receives a screenshot or a CSV export is still asked to trust the party whose conduct is in question. For high-value disputes, that is not evidence. It is a narrative with better formatting.

The regulatory direction is explicit. EU AI Act Article 12 requires high-risk AI systems to keep automatically generated records of events over their lifetime, with traceability appropriate to the system's purpose. The 2026 Visa and Mastercard chargeback rules raise the evidentiary bar for agent-initiated transactions: merchants must show that the agent was authorized to act for the payer, not merely that a checkout session completed. A mutable order log does not answer either question.

The dispute is no longer “did the transaction complete?” It is “was this agent authorized to perform this action, for this principal, at this moment?” That question requires evidence that can be verified independently of the operator.

02Architecture

Sheaf records execution, not intention alone. The recorder sits outside the agent process and observes the same JSON-RPC messages the agent exchanges with an MCP server. Each event is signed, chained, batched, and anchored. The result is a receipt that another party can verify with a pinned public key and a Base RPC.

Interception

A transparent MCP proxy wraps the underlying server. When the agent sends tools/call, the proxy captures the tool name, arguments, and the result returned by the server. It also captures resources/read and sampling/createMessage where configured. Argument and result payloads are hashed; raw payloads are not sent to the recorder by default. The interception point is the boundary itself, not a vendor API and not the agent's own instrumentation.

For runtime enforcement, the same boundary evaluates a sheaf.policy/1 document before the call is forwarded. An ALLOW is recorded and forwarded. A BLOCK or REQUIRE_APPROVAL is recorded with result: "blocked" and returned to the agent as a structured JSON-RPC policy error; the underlying server never sees the call. The audit trail therefore contains both the actions that ran and the actions that were stopped.

Signing

The recorder co-signs each event with Ed25519. The agent never holds the private key, and the wrapped MCP server does not need to be modified. The signed payload is the RFC 8785 (JCS) canonicalization of {v, event, chain}, which makes the signature deterministic across languages and platforms. The agent's own signature is optional; the recorder's signature establishes that the event was observed and chained by the recorder whose key is pinned in the verifier.

Hash-Chaining & Merkle Batching

Every event carries a chain identifier and a sequence number. Its prev_hash is the hash of the previous envelope, excluding signatures. Changing an earlier event changes every later prev_hash, so an edit cannot be hidden by rewriting one record. The recorder periodically batches a contiguous set of events into an epoch and computes a Merkle root over the event leaves. The root commits to the whole batch with a single 32-byte value; any individual event can later be proven against it with a logarithmic-size path.

Anchoring

The epoch root is written to Base L2 in the anchor transaction calldata. The transaction hash and block number are the timestamp and ordering proof: the root existed at a particular block, and no party can retroactively change the events that produce it. Verification pins the expected anchorer address and network, reads the transaction from a Base RPC, and checks that the calldata root matches the Merkle root in the bundle. The chain is self-contained; Sheaf's database is not part of the verification path.

What the chain proves

Ordering, integrity, and the fact that a recorder observed the event before the anchor block.

What the anchor proves

The epoch root existed on a public chain at a specific block, independent of Sheaf's servers.

03Selective Disclosure

A merchant should not have to hand over an entire agent history to prove one transaction. Sheaf uses Merkle-path disclosure: the bundle contains the selected event's signed envelope, its leaf hash, its Merkle inclusion path, and the epoch root. The verifier recomputes the root from the leaf and sibling hashes, then checks the root against the Base anchor. The rest of the epoch stays private.

For a contiguous range, the bundle also includes the events immediately before and after the window. These boundary references prove that the disclosed set is a contiguous slice of the chain and that no event was silently omitted from the middle. Payloads are separately hash-bound: the bundle can include the arguments or result needed to evaluate a claim, or only their hashes when the dispute does not require the raw content.

The result is a portable artifact that supports a narrow claim — “this agent called this tool with these arguments and received this result” — without exposing unrelated customers, tools, or sessions. The same primitive supports the Dispute Bundle's mandate, delegation, consent, execution, and policy evidence.

04Verification

Verification is local and zero-dependency. The browser verifier is a single HTML file with the verification code inlined; it does not load a CDN, a framework, or a Sheaf API. The Node verifier exposes the same checks as a library and CLI. In offline mode it validates the hash chain, signatures, Merkle paths, bundle hash, payload hashes, and evidence structure without making a network request. In online mode it additionally reads the anchor transaction from a Base RPC and confirms the root, anchorer, and block.

Trust is pinned, not discovered. The verifier ships with the recorder public keys and the authorized Base anchorers for its release. A bundle cannot introduce a new key by claiming a URL; the verifier never fetches public_key_url. Rotating a recorder key or anchorer therefore requires a new verifier release, and an old verifier will fail closed on a bundle signed by a key it does not know. The --trust <path> option exists for tests and fixtures, not as a production rotation mechanism.

Offline mode proves integrity, not anchor presence. The anchor_on_base check is reported as unconfirmed, and the CLI exits non-zero unless the caller explicitly accepts an unconfirmed anchor. Online mode is the stronger claim: the record was anchored on Base and has not been altered since execution.

Pinned trust is a feature. It converts key rotation into an explicit software upgrade instead of a runtime trust decision made by the bundle being verified.

Reference Simulation

The architecture is not only described here; it is exercised end to end by a reference simulation that runs on a single machine with no cloud services. A buyer agent is told to purchase a €200 dataset and, if that fails, a €100 one. A policy firewall at the MCP boundary blocks the €200 call before it reaches the merchant and allows the €100 purchase. Both decisions, the denial as well as the sale, are signed by the recorder Worker running locally, hash-chained, and anchored on a local EVM chain standing in for Base.

An independent notary then audits the exported evidence bundle offline. It has only the bundle, the pinned recorder key and anchorer, and an RPC for the anchor chain. It re-checks every signature, Merkle path and anchor. It proves the session is complete rather than a selected subset, and it re-evaluates the policy against the disclosed inputs to confirm each recorded decision. The same run feeds the notary forged variants of the bundle (a hidden denial, a rewritten decision, an altered amount, a substituted policy), and every one is rejected.

The simulation tests the claims in this paper rather than mocking them: the recorder and its anchoring code are the same Worker that runs in production, and the notary builds on the same verification library that ships as @sheafhq/verify.

05Standards Alignment

Sheaf is designed against the emerging set of standards and control frameworks for agent auditability. It is not a certification, and alignment claims should be read as design intent.

  • IETF drafts: hash-chained verifiable observation and log transport (VOLT), agent hash envelopes (AHE), and content-optional audit chains (NHE).
  • EU AI Act Article 12: automatically generated event records, lifetime retention, and traceability for high-risk systems.
  • SOC 2: evidence for monitoring, change management, and integrity of processing — cryptographic records rather than operator-curated screenshots.
  • ISO/IEC 42001: AI management-system traceability, accountability, and lifecycle evidence for autonomous actions.
  • RFC 8785 (JCS): deterministic JSON canonicalization for cross-platform signature verification.

This document describes protocol behavior. It is not legal advice, and it does not replace a regulator's or card network's assessment of a specific dispute.
